Build the approved web slice: $ARGUMENTS

Read first: `docs/adr/0016-web-stack.md`, `docs/engineering/frontend.md`, `.claude/rules/web.md`, and the OpenAPI operations the screen uses. Decisions already made by the owner (do not reopen them): Next.js with strict TypeScript, Tailwind CSS with shadcn/ui, a client generated by `openapi-typescript` and `openapi-fetch`, and the sign-in token held by the Next.js server in an httpOnly cookie so the browser never sees it.

**Before any code.** Every screen needs its API. If an endpoint is missing, that is a backend slice: stop and run `/plan-slice` for it (API first, DEC-004). If this is the first web slice, the scaffold itself (apps/web, scripts, CI job, `make gen` extension) is its own approved plan.

**Order of work.**
1. **Plan the screens** in plain language from the spec's user stories (`US-*`): who uses it, what they see, which permissions show or hide actions. Ask the owner about any UX choice that changes a workflow (`/ask-human`); do not invent business flows.
2. **Generate the client**: extend `make gen` so `apps/web/src/api/schema.d.ts` is generated from `api/openapi/openapi.yaml`; CI fails if it is stale (same rule as Go). Never hand-write a call to our API.
3. **Server side first**: the Next.js route handlers that call the API with the token from the cookie (sign in with OTP, sign out, a typed proxy). Test these before any UI.
4. **UI**: server components by default; client components only for interaction. Every user-visible string comes from the message catalogue (English now, Urdu later; no hard-coded product name, DEC-015, DEC-017). Plain-language labels from the glossary: the accountant never sees "debit" or "credit" on a primary screen. Show money from `{amount, currency}` with one formatter; never do arithmetic on floats.
5. **Permissions in the UI are a convenience, not security.** The API enforces them. Hide what the user cannot do, and handle 401 (sign in again) and 403 (clear message) everywhere.
6. **Accessibility**: keyboard reachable, visible focus, labels on inputs, sufficient contrast, errors tied to fields.

**Tests (all must exist before the slice is done).**
- Unit and component tests with Vitest and Testing Library for formatters, validators and components with logic.
- End-to-end tests with Playwright against the real API and database: sign in, the main happy path, each refusal the user can see (wrong code, missing permission, validation errors), and a second school cannot see the first school's data. Use the `playwright` MCP server to explore a page while building, then encode what you learned as a Playwright test.
- Accessibility check with axe in the Playwright run.
- Contract drift: regenerate the client and require no diff.

**Evaluate.** `npm run lint && npm run typecheck && npm test && npx playwright test`, plus `make evaluate` for the backend, then `/verify`. Take screenshots of each screen at a phone width and a desktop width and look at them; report what looks wrong instead of calling it done.

**Standards.** Small components, no global state libraries until needed, no new dependency without an ADR, no secrets in `NEXT_PUBLIC_*`, no tokens in `localStorage`, no `any`.

Report as in `/verify`, and list the screens covered, the user stories covered, and anything that needs a human decision.
