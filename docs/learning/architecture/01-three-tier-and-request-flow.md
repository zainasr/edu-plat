# 01. Three-tier architecture and a full request flow (with a real example)

## 1. The three tiers

```
┌──────────────────────────────────────────────┐
│ Tier 1: Presentation / client                │  Next.js web, React Native apps, curl
│   - shows screens, collects input            │
└───────────────────┬──────────────────────────┘
                    │ HTTPS JSON (the OpenAPI contract)
┌───────────────────▼──────────────────────────┐
│ Tier 2: Application / business logic         │  Go API (modular monolith)
│   handler  -> HTTP only: decode, respond      │
│   service  -> business rules, transactions    │
│   store    -> SQL (sqlc), no rules            │
└───────────────────┬──────────────────────────┘
                    │ SQL (pgx), transactions, RLS
┌───────────────────▼──────────────────────────┐
│ Tier 3: Data                                 │  PostgreSQL (+ standby, backups)
│   tables, constraints, RLS, journal rows     │
└──────────────────────────────────────────────┘
          plus: external systems (aggregator, WhatsApp BSP, FCM)
          called from the service layer, never from the browser
```

**Why three tiers and not two?** Keeping rules out of handlers means the same rule works for the web portal, the mobile app and a terminal script (DEC-004). Keeping SQL out of services means you can change or test queries without touching business rules.

### Node/Next.js comparison
| Tier | Typical Next.js + Node | Our Go API |
|---|---|---|
| Presentation | React pages, server components | Next.js (same role) |
| Handler | Route handler, `app/api/.../route.ts` or Express route | `internal/<module>/http.go` |
| Service | Plain functions or a class in `lib/` | `internal/<module>/service.go` |
| Store | Prisma or raw `pg` calls | `internal/<module>/store/` (sqlc) |
| Data | Postgres | Postgres |

## 2. The layers inside one module

```
internal/fees/
  fees.go       public types and the small interface other modules may use
  http.go       handler: parse request, call service, write response
  service.go    rules: fee payer lookup, allocation, journal entry, events
  store/        queries.sql (source), generated Go (never edited by hand)
```
Rule: a layer may call only the layer directly below it, plus interfaces it was given. Handlers never touch SQL. Stores never read HTTP headers.

## 3. Full request flow: recording a cash payment

**Scenario:** Ms. Rubina at the reception desk records Rs 12,000 cash for a family with three children (REQ-FEE-021, US-FEE-002). The browser sends:

```http
POST /api/v1/payments HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...          (session token, issued at login)
Idempotency-Key: 7f3c2a1e-...                (generated by the browser for this one click)
Content-Type: application/json

{ "family_id": "f-…", "method": "cash", "account": "Cash in Hand", "amount": { "amount": 1200000, "currency": "PKR" } }
```

### Step by step

**Step 1. Server accepts the connection (runtime).** `net/http` starts a goroutine for the connection and reads the request. See note 05.

**Step 2. Router matches the route.** `ServeMux` matches `POST /api/v1/payments` and sends it to the middleware chain.

**Step 3. Middleware runs, in order:**
1. *RequestID*: uses the incoming `X-Request-ID` or creates one; stores it in the context.
2. *Logging*: records the start time (logs the result at the end).
3. *Auth*: verifies the bearer token, reads `tenant_id` and `user_id` from it, and puts them in the context. The request body is never trusted for tenant.
4. *Permission check*: the user must hold `fees.collect` (the union of all their roles, DEC-006).

If any step fails, the chain stops. For example, a missing token returns `401` before any business code runs.

**Step 4. Handler decodes and validates the body (`http.go`).**
```go
var in RecordPaymentRequest
if err := decodeJSON(w, r, &in); err != nil { httpx.WriteError(w, err); return }
```
Checks shape and types only: amount is a positive integer, method is one of the allowed values. It does not check whether the family owes money.

**Step 5. Handler calls the service with the context.**
```go
receipt, err := h.svc.RecordPayment(r.Context(), in)
```

**Step 6. Service applies the rules (`service.go`).**
1. Idempotency: looks up `Idempotency-Key` for this tenant. If the same key was already used, returns the **original** receipt and does nothing else (REQ-API-010). Retried double-clicks cannot take money twice.
2. Asks the students module for the family's fee payer (through the interface, not its tables).
3. Calculates the allocation: oldest challan first (REQ-FEE-022).
4. Builds the journal: debit `Cash in Hand` Rs 12,000; credit `Fees Receivable` Rs 12,000, in paisa (DEC-016).
5. Opens **one database transaction** and calls the store.
6. After commit, publishes `payment.recorded` for the notifications module (asynchronous).

**Step 7. Store writes inside the transaction (`store/`).** All statements run in one `BEGIN … COMMIT`:
```sql
set_config('app.tenant_id', $1, true);            -- RLS: this transaction sees only this school
insert into payments (...) values (...);          -- append-only
insert into receipts (number, ...) values (...);  -- number from a sequence, never reused
insert into journal_lines (...) values (...), (...);  -- balanced: debits = credits
update challans set status = 'partial' where ...; -- status only; amounts are never edited
insert into idempotency_keys (...);               -- remembers the result for retries
```
If any statement fails, the whole transaction rolls back. Either all rows exist or none do.

**Step 8. Response is written.** The handler returns `201 Created` with the receipt. The body follows the API conventions (money in minor units, ISO dates, IDs as UUIDs). The browser prints the receipt.

**Step 9. Background work (asynchronous).** The notifications module receives `payment.recorded` and enqueues a WhatsApp or in-app message for the fee payer. If WhatsApp is down, the job retries; the payment is already safe.

**Step 10. Logging and metrics.** The logging middleware writes one line with method, route, status 201, duration and request ID. The counter `payments_recorded_total` increases.

### Timeline in one picture

```
t=0ms    request arrives, goroutine starts
t=1ms    middleware: request ID, auth, permission ok
t=2ms    decode body, call service
t=3ms    idempotency key not seen -> continue
t=4ms    BEGIN; write payment, receipt, journal, challan status
t=12ms   COMMIT (database confirms durability)
t=13ms   201 Created written; event published
t=14ms   log line: 201, 13 ms, request_id=…
later    worker sends the receipt message
```

### What goes wrong, and where it is caught
| Failure | Caught at | Result |
|---|---|---|
| Expired token | Auth middleware | 401, nothing written |
| Missing permission | Permission check | 403, nothing written |
| Amount is text | Handler decode | 400, nothing written |
| Family has no challans | Service | 422 with a clear message; nothing written |
| Double click | Service idempotency | Same 201 and receipt returned; nothing written twice |
| Database down mid-write | Transaction | Rollback; 503; client retries with the same key safely |
| App crashes after commit, before reply | Idempotency key | Client retries; the original result is returned |

## 4. The same flow for a read: fetching dues

`GET /api/v1/families/{id}/dues` follows the same path with no transaction for writes: middleware → handler → service → store `select` → JSON. It is simpler because it has no side effects, so it can be retried freely.

## 5. Cross-module calls, in one line each
- `fees` asks `students` through an interface (note 04).
- `fees` publishes `payment.recorded`; `communication` subscribes (no direct call).
- Nothing calls the aggregator from a handler. Webhooks arrive at a dedicated endpoint, are signature-checked, and then processed like any command.
