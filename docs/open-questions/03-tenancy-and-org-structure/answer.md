# 03 Answers

1: [accepted, but make it simple] Model: Organisation -> Institution -> Branch -> Shift -> Class -> Section. 1.0 UI: single organisation with one institution and multiple branches and shifts (an owner with two institutions of different types gets one organisation login with an institution switcher, but that UI can be basic). Data model supports all levels from day one.
2: [accepted] Tenant = Organisation (subscription, data isolation, billing, owner). Institution/branch are scoped objects inside the tenant.
3: [accepted] Shared per institution: students, staff directory, fee types, chart of accounts. Branch-scoped: classes/sections, timetables, attendance, fee collection and cash books (cash drawer per branch), expenses, staff assignment. Reports can be viewed per branch or consolidated.
4: [accepted] Shift is a property of a section (Class 5-A Morning vs Class 5-A Evening are different sections). Shifts carry their own timings (start/end/period length), timetable, attendance rules; fees default from class but can be overridden per shift.
5: [accepted] Session has start/end date, one "current" per branch, overlaps allowed only during rollover. Editing dates allowed until first attendance is marked; afterwards only extend. Rollover wizard: copy classes/sections/subjects/fee structure, then promote students (see section 04).
6: [accepted] Terms belong to a session (3 or 6, with name, dates, weightage) and are used for exam grouping and report cards; optional "term fee" mode later. Not tied to fees in 1.0.
7: [accepted] Provide a template library by level (Early years, Primary, Middle, Secondary, Higher Secondary, O/A levels, college ADP/BS) that an institution picks from, and custom classes always allowed. Grade number kept for ordering and promotion mapping.
8: [accepted] Store board/curriculum as a label on class/institution (Punjab Board, Federal, Cambridge, other) for later result formats and syllabus templates; no board-specific logic in 1.0.
9: [accepted] 1.0: academies use the same Class/Section structure, labelled "Batch/Course" by institution type, with per-student fee override. Subject-wise/per-course fees and flexible enrolment (student in multiple batches) are a 1.1 item.
10: [accepted] Calendar at institution level with branch overrides: weekly off days, holidays/events with date range, special working days, optional timing overrides (Ramadan). Holidays suppress attendance and fee due reminders.
11: [accepted] Name, short name, registration no optional, NTN (optional), logo, principal signature image, stamp optional, address, phones, WhatsApp, email, website (optional), bank accounts (for challans), letterhead settings optional, board , type, established year, branch details.
12: [can be but not priority to do implment] States: Trial -> Active -> Grace (7 days overdue, read/write with banner) -> Suspended (read-only, parents still can see/pay) -> Archived (30 days, export offered) -> Deleted (after 90 days on request, with legal hold exceptions). Data export always available to owner.
13: [It totally depend upon the institue to institure rather than format we provide they choose own way] Reg no: configurable prefix + year + sequence per institution (branch code optional). Import allows existing numbers (must be unique).
14: [accepted] Yes, via two enrolments (different sections/shifts/branches) under one student record; fee and attendance are per enrolment. Hidden behind an advanced toggle in 1.0.
