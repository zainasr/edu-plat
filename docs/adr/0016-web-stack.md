## Context
The spec fixes the web app as Next.js with TypeScript (DEC-005). It does not choose the styling approach, how the browser calls our API, or where the sign-in token lives. These shape every screen, the generated client, the tests and the security of sessions, so they are decided once, before any frontend code exists.

## Options considered

**Styling and components**
1. **Tailwind CSS with shadcn/ui.** Components are copied into the repo and owned by us, built on accessible primitives; no heavy runtime library to upgrade; plain files an AI agent can read and change.
2. **Mantine.** Faster first screens (forms, tables, date pickers included) but a large dependency whose upgrades we do not control.
3. **Plain CSS modules.** No dependency, but every table, form and dialog is hand-built.

**API client**
1. **`openapi-typescript` with `openapi-fetch`.** Generates types only, plus a tiny typed fetch wrapper. Small, easy to review, fits `make gen` and the CI freshness check.
2. **`orval`** generating TanStack Query hooks. Less code to write, a larger generator and generated runtime.
3. **Hand-written fetch with generated types.** Most control, most upkeep, and the existing rule says not to.

**Where the token lives**
1. **The Next.js server holds it in an httpOnly cookie** and calls the API for the browser (a backend for the frontend). The browser never sees the bearer token, so injected script cannot steal it. The API stays unchanged: bearer tokens still serve curl, scripts and mobile.
2. **The browser holds the token and calls the API directly.** Simplest, but any injected script can read it, and it needs CORS on the API.

## Decision
1. Tailwind CSS with shadcn/ui.
2. `openapi-typescript` with `openapi-fetch`, regenerated by `make gen` and checked for drift in CI.
3. The Next.js server keeps the session token in an httpOnly, Secure, SameSite=Lax cookie and attaches it when calling the API. The browser never receives a bearer token.

Testing stack that follows from these: Vitest and Testing Library for units and components; Playwright for end-to-end tests against the real API and database, with axe for accessibility.

## Consequences
- Good: the API contract stays the single source of truth; the web client cannot drift (generated types, CI check); a stolen script cannot read the session; every UI piece is a file we own.
- Bad: shadcn components are our code to maintain; the Next.js server must be deployed beside the API and added to the pipeline and runbooks; a second place (route handlers) handles sign-in, so it needs its own tests.
- Follow-ups: this ADR does not scaffold anything. The first web slice is planned separately (`/plan-slice`) and includes the scaffold, the CI job and the `make gen` extension. A new frontend dependency still needs its own ADR. Mobile (React Native) is decided separately.
